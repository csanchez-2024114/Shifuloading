# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Copia aislada del agente Shifu (LangGraph) con auth, catálogo de apps y funciones de apps, sobre FastAPI + MongoDB. Mantiene el layout `app/...` del backend original, así que los imports no cambian. **No arranca los workers de Redis** (workflow/trigger/notifier/reflection): el código de workflows está copiado, pero solo lo disparan "ejecutar ahora", el webhook y, con `SHIFU_SCHEDULER=1`, el programador en el mismo proceso (ver "Crear workflows por chat"). Los docs, tests y comentarios llaman "agente_v3" a lo que está en `app/agent/shifu_base_v1/`.

- **Proceso al cambiar el agente:** pytest → nodo suelto → agente completo con `--only`; luego subir `AGENT_VERSION`, entrada en `doc/agente/CHANGELOG.md` y `python scripts/snapshot_prompts.py`.
- **Datos en Mongo:** se cambian con un script chico que fija el campo (`update_many` + `$set`), no volviendo a correr el seed (pisa lo editado). Después hay que reiniciar el backend: la personalidad tiene caché de 10 minutos.
- **Modelos:** el agente solo usa gpt-4o-mini y gpt-4.1-nano.
- **Heredocs de Bash en Windows:** en esta configuración rompen las barras invertidas (`\n`, regex) aunque el delimitador vaya entre comillas. El código que las lleva se edita con las herramientas de edición.
- **Documentos para retomar:** `doc/agente/PENDIENTES.md` (qué falta), `doc/agente/INVESTIGADOR.md` (búsqueda web), `doc/funciones/` (sistema de funciones).

- **Versionado y bitácora del agente** (`doc/agente/`). Para cambiar el agente se sigue el proceso de `CHANGELOG.md`.
  - `AGENT_VERSION` está en `app/agent/version.py`. Cada respuesta (`usage.agent_version`), traza y corrida lleva `<versión>+<huella de los prompts en Mongo>`.
  - `eval_agent.py` agrega una línea a `BITACORA.md` y crea un usuario por conversación (la memoria contaminaba escenarios). Los turnos con `"new_conversation": true` siguen con el mismo usuario.
  - En local hace falta `RATE_LIMIT_ENABLED=false`, porque el registro está limitado a 3/min.
  - Cada bug arreglado se vuelve un escenario en `scripts/eval_scenarios.json`.
  - Además del set fijo, `eval_agent.py --generate N` genera escenarios nuevos por corrida (`scripts/gen_scenarios.py`): el código sortea las dimensiones de `scripts/eval_dimensions.json` y un mini agente escribe el diálogo. Para cubrir casos nuevos se agregan valores a ese JSON.
  - El juez del evaluador solo clasifica la cita de cada prohibición (`evidence_stance`) y el código decide si hubo violación, porque leía la negación al revés.
- Mongo (`MONGO_URI`, README indica :27018) es obligatorio. Redis (`REDIS_URL`, :6380) es opcional: sin él la cuota de mensajes deja pasar y el circuit breaker/rate limit de herramientas no actúa.
- Para OCR hacen falta Tesseract (con idioma `spa`) y Poppler en el sistema.
- No hay linter ni formateador configurado.
- `SHIFU_DEV_MODE=true` imprime cajas de depuración por nodo (`stage_logger`, `log_utils`). `SHIFU_LOG_SYSTEM_PROMPT=1` registra el prompt completo del `responder`. `SHIFU_DEV_UI=1` (solo local) monta la interfaz `/ui` y permite que el chat devuelva trazas con los prompts completos (`"trace": true`); sin él ambas cosas están apagadas. `SHIFU_TRACE_LOG=1` guarda **cada turno completo** en `logs/agent_traces/AAAA-MM-DD.jsonl` (todas las llamadas a un modelo con sus mensajes completos, salida, tokens, costo y etiqueta del mini agente, más la salida de cada nodo, reintentos y errores); se lee con `python scripts/review_traces.py [--last N] [--conv ID] [--full] [--anomalies]`. Es para auditar si cada mini agente actuó bien (Claude hace de evaluador leyendo ese log). Guarda los prompts tal cual, incluido lo que el usuario escribió (contraseñas incluidas): solo desarrollo, `logs/` está fuera de git.
- La configuración está en `config.py` (raíz, `from config import Config`). `load_dotenv()` debe correr **antes** de importar `app.*`, porque `ChatOpenAI` y `OpenAIEmbeddings` se crean a nivel de módulo.

## Arquitectura

**Un solo grafo LangGraph**, definido en `app/agent/shifu_base_v1/graph/builder_standard.py`, con nodos en `app/agent/shared/nodes/`. `registry.py` lo compila con el checkpointer `MongoDBSaver` que crea `main.py` (colecciones `shifu_checkpoints` y `shifu_checkpoint_writes`); `thread_id = conversation_id`.

```
START → goal_resolver → memory_retriever → semantic_intake ─┬─ (flujo de requisitos activo) → req_investigator ─┐
                                                            ├─ (cierre / cuenta elegida) ───────────────────────┤
                                                            └─ catalog_checker, auth_validator,                 │
                                                               tavily_subgraph, document_analyzer (paralelo)    │
                                                               → fan_in → (act: action_runner |                 │
                                                                           command: workflow_manager) ──────────┤
                                                                                                                 ▼
                                      memory_updater ← response_evaluator ⇄ responder (reintenta hasta 2 veces con eval_feedback)
```

`tavily_subgraph` es `tavily_searcher → research_curator → research_analyst`. `semantic_intake` decide el camino en `_route_from_intake`; después de `fan_in` la intención manda: `act` → `action_runner`, `command` → `workflow_manager`, el resto directo al `responder`. Cualquier fallo de un nodo envuelto con `_safe_node` pone `agent_error` y manda el turno a `error_handler`.

### Estado (`graph/state.py`) y reglas que causan bugs

- `ShifuInputState` es lo que manda el handler de chat; `ShifuOutputState` es lo que devuelve `ainvoke`.
- `semantic_intake` reinicia los campos del turno con `_EMPTY_RESULT`. Un campo nuevo por turno debe agregarse ahí, o se hereda del checkpoint anterior.
- Reducers: `validation_reports` usa `_reset_or_add` (`None` vacía, lista agrega). `selected_accounts`, `available_accounts` y `session_documents` usan `_merge_dicts`, donde `None` significa "sin cambios" y **nunca se quitan llaves**.
- Las 4 ramas paralelas deben escribir campos distintos. Los comentarios del código explican varios conflictos de escritura concurrente (p. ej. por qué `semantic_intake` no reinicia `user_connected_apps`).
- `tavily_subgraph` es un subgrafo compilado; `_tavily_with_timeout` devuelve solo 3 campos para no pisar los de otras ramas.

### Transporte de chat (`app/routes/chat/chat.py`)

`/ws/chat` (WebSocket) y `/chat/stream` (SSE) comparten `_build_input` y `_ChatStreamer`. El `conversation_id` lo manda el cliente y es el `thread_id` del checkpoint: `_owned_by_other` (también en `debug_ws`) rechaza con 404/4004 si ya pertenece a otro usuario en `chat_context`. El streamer envía tokens solo de los LLM con el tag `shifu-chat` y emite `agent_status` con las etiquetas de `graph/node_labels.py`. Al terminar manda `done` (con `ui_actions` de `_build_ui_actions`) y luego `sources`. `chat_cli.py` y `app/routes/ws/debug_ws.py` reutilizan estas piezas. El conteo diario de tokens solo está en la ruta SSE.

### Crear workflows por chat (`graph/req_nodes.py`)

`req_investigator` tiene 3 pasos (v0.6.5; antes 6 niveles que iban y volvian y nunca activaban), en `req_level` (`REQ_GATHER`=1, `REQ_CONFIRM`=4): **GATHER** (`_gather`) marca las apps conectadas (si falta una, pide conectarla y no arma nada), planea con funciones reales y pregunta SOLO lo que falta, una por turno (`req_pending_questions`); **CONFIRM** (`_present`) guarda el borrador en "creating", corre `execute_dry_run` y manda UN mensaje (plan en palabras llanas, simulacion, cuando corre, "¿Lo activo asi?"); al responder (`_confirm_stage`): confirmar → `_finalize` activa y programa, cambiar → rehace el plan con la correccion, cancelar → borra el borrador; si el clasificador falla no se activa. `semantic_intake` activa el flujo con la intencion `create_workflow` y clasifica cada turno (`continue`/`cancel`/`digress`). **Relevo:** en los turnos del flujo (`req_relay`) el responder entrega el mensaje TAL CUAL, sin modelo, y el evaluador no lo reescribe (con la orden de "transmitir fiel" el modelo quitaba el horario y la pregunta e inventaba requisitos); el streamer emite el mensaje completo. El plan usa funciones reales: `_build_plan` ofrece candidatas (`app/functions/select.py`: apps conectadas y nombradas, sin `delete` ni `gmail.drafts.send`, tope 30 repartido por app), el modelo (modo JSON) devuelve `function_id` + `args` y el codigo valida todo (`_check_plan`: id inventado se descarta, dato faltante o marcador `<...>` se pregunta, plantillas `{{step_N.campo}}`/`{{step_N.rows[0][1]}}` solo a pasos anteriores; las apps sin funciones conservan el paso estilo viejo). Se guarda `function_id`, `config=args` y `account_id` (solo si hay una cuenta). Se mide con `scripts/eval_workflow_plan.py` y el escenario `wf_programado`.

**Disparadores** (todos pasan por `app/services/workflow_launcher.py::start_workflow_run`: límite de corridas del plan, `create_run`, ejecución en segundo plano): `POST /workflows/{id}/run` (manual), el programador y `POST /api/v1/webhooks/{token}` (`routes/workflows/webhook.py`; el token es la autenticación, 404 genérico, 409 si el workflow no está `active`, 413 sobre 64 KB, 30/min por IP+token y 120/min por IP; responde 202 `{run_id}`). El programador (`app/workers/scheduler_loop.py`) arranca en el `lifespan` solo con `SHIFU_SCHEDULER=1`; cada `SHIFU_SCHEDULER_TICK_SECONDS` (30) reclama con `claim_due_task` (atómico), pausa la tarea si el workflow no existe o no está activo, lanza con `trigger="schedule"` (simula si `SHIFU_FUNCTIONS_SIMULATE=1`) y llama a `advance_or_complete`. El cron se lee en `schedule_config.timezone` (IANA; `state.user_timezone`; sin zona, UTC) y se guarda en UTC. El nivel 6 ya no depende de `schedule_context.cron` del turno: parsea `req_trigger_event` con `chrono_parser.parse_schedule` y, si no hay horario, pregunta una vez (`req_schedule_asked`) en vez de decir que quedó activo. Los pasos leen el JSON del webhook con `{{trigger}}` / `{{trigger.campo}}` (`run["trigger_payload"]`, conserva el tipo si ocupa todo el valor). **Disparador por correo (v0.7.0):** el planificador devuelve `trigger_type: "email"` y `trigger_filter` (consulta de Gmail); `_finalize` guarda `email_trigger {q, account_id, since, seen_ids, next_poll_at}` en el workflow y `app/workers/email_trigger_loop.py` (lo llama el mismo ciclo del programador, cada `SHIFU_EMAIL_POLL_SECONDS`, 120) reclama de forma atomica, corre `gmail.messages.search` con `in:inbox after:<since>` y lanza una corrida por correo no visto con `trigger="email"`; los pasos leen `{{trigger.sender|subject|snippet|date|id}}` (`_check_plan` rechaza otros campos). `auth_expired`/`missing_connection` apagan el disparador (`email_trigger.disabled`); es sondeo, no push.

### Memoria

`app/agent/shared/memory/` más `helpers/context_ranker.py`: `memory_engine` lee 5 tipos en paralelo (metas, semántica, episódica, decisiones, preferencias). Metas, decisiones y preferencias pasan por el ranker (top 5 → `ranked_context` → `MEMORY CONTEXT`). Los hechos del usuario (`user_semantic_memory`, **un documento por hecho**, el mismo esquema que `/me/memories`) y el diario (`user_daily_diary`, un documento por conversación con `activities` y `pending`; se excluye la conversación actual) van fuera del ranker en `user_memory_context`: bloque "## What you remember about the user" del responder, y el juez lo recibe como evidencia. Escribe `memory_learner` (llamado por `memory_updater` en cada turno salvo `system_event`, dentro del grafo, así sale en la traza con la etiqueta `memory_learner`). Su criterio es dato: `agent_personality.memory_policy` (`enabled`, `model`, `remember`, `never`, `suggested_keys`, `usage`); en código solo hay una guardia contra credenciales y el descarte de hechos repetidos sin cambio. Modelo: gpt-4o-mini (nano conservó un dato que el usuario corrigió, 0 de 3). **Preferencias vigentes (v0.9.9):** el responder repite al FINAL del prompt los hechos con clave en `memory_policy.standing_keys` (por defecto `language`, `preferences`; texto en `standing_note`), porque a mitad del prompt guardaba "respóndeme en inglés" y contestaba en español; las metas se guardan con la clave `goals`. El saludo usa el diario vía `greeting_behavior.first_message`; "hola" a secas (atajo `_TRIVIAL_RE` de `semantic_intake`) se marca como intención `chat` para que aplique. La UI de pruebas muestra y borra los hechos ("Lo que Shifu recuerda"). `memory_updater` además guarda decisiones con embedding (solo en `level_2` con `ranked_context`). Las metas solo se leen. **Compromisos con fecha** (`memory_policy.commitments`, default `{enabled: true, horizon_days: 3}`): `memory_learner` guarda `due_date` (YYYY-MM-DD, resuelta contra `state["current_time_utc"]`, nunca `datetime.now`) en el diario, recibe los pendientes con fecha de otras conversaciones y devuelve `closed` (ids que el usuario dio por hechos → `done_at`, solo del mismo `user_id`); `load_commitments` (episodic_memory_helper) los lee vencidos o por vencer y `format_user_memory` los pinta en "Commitments with a date". **Avisos (v0.7.1):** `user_notifications` (rutas `/api/v1/me/notifications`) recibe `run_completed`/`run_failed` (ejecutor), `trigger_disabled` (el disparador de correo se apagó) y `commitment_due` (`app/workers/reminder_loop.py`, en el ciclo del programador: un aviso por compromiso que vence hoy o venció hace ≤7 días, una vez por `reminded_at`; "hoy" es UTC). En el PRIMER mensaje de una conversación `memory_retriever._notices` toma los no leídos de `memory_policy.notices` (`{enabled, max, types}`, por defecto `run_failed` y `trigger_disabled`) con `take_untold`, que los marca `told_at` (se dicen una vez; siguen sin leer en la lista) y devuelve solo texto (un ObjectId en el estado rompe el checkpoint). Bloque "Notices the user has NOT seen yet". **Por correo (v0.7.2):** `app/workers/notice_mailer.py` (ciclo del programador, solo con `SHIFU_NOTICE_EMAILS=1` y `SMTP_*`) junta en UN correo por usuario los avisos sin leer de menos de 24 h (`run_failed`, `trigger_disabled`, `commitment_due`; `SHIFU_NOTICE_EMAIL_TYPES`), marca `emailed_at` antes de enviar, respeta `users.email_notices` (`PATCH /me/preferences`), tope `SHIFU_NOTICE_EMAIL_DAILY_CAP` (5 en 24 h, colección `notice_emails`) y no reintenta un envío fallido (`email_error`). Con `SHIFU_DEV_UI=1` el body SSE acepta `now` (ISO UTC) como reloj simulado; `eval_memory.py` lo manda con `"now"` por sesión (caso `compromiso_fecha`).

### Búsqueda web (`nodes/tavily_searcher.py`, `research_curator.py`, `research_analyst.py`)

`semantic_intake` decide `needs_external_info`, la consulta, `search_recency` (`day|week|month|any`; `any` = sin filtro, para datos estables y documentación: un filtro de "último año" escondía las páginas oficiales) y `search_topic` (`news|general`). `tavily_searcher` los pasa a Tavily, amplía la ventana si no hay resultados y escribe `research_freshness` (ventana usada + fecha de hoy) para el responder y los jueces. El lugar del usuario NO se pega a la consulta. Cómo responder con lo encontrado es dato: `prompt_snippets.web_found` / `web_unavailable`. **Juicio (v0.9.5):** después del curador, `research_analyst` (4o-mini, criterio en `agent_personality.research_policy`) razona sobre las fuentes y pone al inicio de `curated_research` conclusión, confianza, advertencias y fuentes descartadas; puede pedir UNA búsqueda más. La comparación de fechas es código (`_already_past`): si una fuente llama "próximo" a algo cuya fecha ya pasó, se fuerza la segunda búsqueda (el mini fallaba esa resta). Se mide con `scripts/eval_web.py [--n 6 | --all] [--judge] [--match texto]` (sortea temas de un banco; intake + Tavily reales, sin responder) y los escenarios `web_*`.

### Modo act (`nodes/action_runner.py`, v0.5.0)

Con la intencion `act` (pedido puntual de datos de sus apps), `fan_in` manda el turno a `action_runner`: busca por embeddings funciones de `app/functions` dentro del cerco (apps conectadas o nombradas, solo lectura, estado en `SHIFU_FUNCTIONS_STATUSES`, por defecto `active`) y 4o-mini las llama en paralelo (`action_policy` en Mongo: `max_parallel`, `max_rounds`, `max_calls`). Resultados en `action_results` → bloque del responder y evidencia del juez; `actions_backed` (codigo) impide presentar datos de una app cuyas llamadas fallaron. En local: `SHIFU_FUNCTIONS_SIMULATE=1 SHIFU_FUNCTIONS_STATUSES=active,testing,draft`. **Cuentas por código (v0.9.2):** `action_runner` ofrece siempre `calculate` (aritmética segura con `ast`, `helpers/calc.py`) y `aggregate_column` (sum/avg/min/max/count sobre una columna de la tabla ENTERA que devolvió una función, con filtro opcional); salen en `action_results` como `shifu.calc.*`. Se mide con `scripts/eval_calc.py`; las tareas de varios pasos con `scripts/eval_multistep.py`. **Instrucciones escondidas (v0.9.0):** lo que devuelve una función es dato, no orden (regla en `_METHOD` y en el bloque del responder). Por código: una escritura retenida que usa un correo que el usuario NO escribió, cuando el usuario sí dio uno, se rechaza (sustitución de destinatario); cualquier otra dirección o enlace ajeno queda en `foreign` y la confirmación lo advierte (`describe_calls`). Se mide con `scripts/eval_injection.py` (~$0.01). Medir barato: `scripts/eval_function_search.py` (busqueda, ~$0) y `scripts/eval_action_runner.py` (nodo aislado, ~$0.04).

### Administrar workflows por chat (`nodes/workflow_manager.py`, v0.9.1)

Con la intencion `command` (preguntar por o actuar sobre un workflow que YA existe), `fan_in` manda el turno a `workflow_manager`: 4o-mini con herramientas locales sobre Mongo, todas filtradas por `user_id` (`list_workflows`, `get_workflow` con las ultimas 3 corridas y el paso que fallo, `pause_workflow`, `resume_workflow`, `set_schedule`, `run_now`, `delete_workflow` = archivar, se recupera con resume). El nodo le da al modelo la lista con ids por delante (sin eso adivinaba ids) y la agrega a `action_results` (`"auto": True`) para que el responder explique con el estado real aunque no se llame nada. Escribe `action_results`/`action_stop` con la forma de `action_runner` (app `shifu`), asi el bloque del responder y `actions_backed` sirven igual. Tope: 4 vueltas, 8 llamadas. `run_now` no pide confirmacion. Escenario `wf_administrar`. El programador tambien corre aparte: `python -m app.workers.scheduler_loop`.

### Herramientas (BigTools, sistema viejo)

**Desde v0.8.0 el agente ya no lo usa:** `bigtools_inspector` y `workflow_planner` salieron del grafo, `platform_context` solo lee `app/functions` y el flujo de workflows no crea pasos sin `function_id`. El código sigue en el repo hasta la etapa 2 (se borra tras probar con cuentas reales); lo de abajo describe ese código.

- El chat no ejecuta herramientas de BigTools (el modo act usa el sistema nuevo de funciones). `bigtools_inspector` solo le pregunta a un LLM cuáles servirían. Las ejecuta `WorkflowExecutor._call_tool` (`app/workers/workflow_executor.py`) con rate limit, circuit breaker (Redis), timeout por paso y `tool_outcome_log`.
- `app/services/bigtools_loader.py::get_all_bigtools` importa por reflexión cada `get_*_bigtools` de `app/agent/shared/tools/providers/` y le pasa solo los parámetros que su firma declara. Los módulos que no existen se saltan sin error visible. Los conectores reales (API y credenciales) están en `app/tools/connectors/`.
- Hay **dos listas de nombres de herramientas que se mantienen a mano**: lo que existe en los providers y lo que cree el inspector (`app_tools_catalog` en Mongo, con respaldo en `BIGTOOLS_REGISTRY` de `helpers/bigtools_registry.py`). Al agregar una herramienta hay que actualizar ambas.
- Solo gmail, drive, docs, sheets, slides, dropbox, clickup, asana, facebook y hubspot tienen tools; el resto de integraciones solo tiene OAuth.

### Funciones de apps, sistema nuevo (`app/functions/`, aditivo; docs en `doc/funciones/`)

Convive con BigTools; lo usan el modo act y `WorkflowExecutor` (pasos con `function_id`). Cada app es un paquete `app/functions/apps/<app>/` (`app_spec.py` con su `AuthSpec`, `functions.py` con los handlers); la plantilla es `apps/_template/`.
Una funcion = ficha (`FunctionSpec`, versionada) + handler `async def f(ctx, args: Modelo) -> Modelo`; devuelve siempre un `Result` (`{ok,data}` o `{ok:false,error}`, diez codigos; `access_denied` = 403 de Google sin acceso a ese archivo). `get_connection` lee **solo `user_connected_accounts`** (multicuenta; refresco y marcado de cuenta vencida por `_id` exacto). La autenticacion es un registro de estrategias (`none`, `api_key`, `bearer`, `basic`, `custom_params`, `oauth2_code`; `oauth1`, `oauth2_client_credentials` y `hmac_signature` declaradas sin implementar). El registro **falla en voz alta** (el loader viejo salta en silencio). `/internal/functions/{id}/test` prueba una funcion con una o varias cuentas del propio usuario; lo que no es lectura se simula salvo `allow_write`.
Tests: `test/functions/conftest.py` fija entorno falso (sin `.env`, Mongo ni Redis); usa `mongomock-motor` porque el `FakeDB` de `test/agente_v3` ignora los filtros con operadores.

### Piezas que no se ven desde el grafo

- Identidad y personalidad (`agent_identity`, `agent_personality`) se leen de Mongo con caché de 10 minutos (`helpers/identity_loader.py`) y definen el prompt fijo, el saludo y las señales de despedida.
- **UI actions (v0.10.0):** catálogo en Mongo `ui_actions_catalog` (`helpers/ui_actions.py`, caché 10 min; `scripts/seed_ui_actions.py` carga la lista de prueba). `source: "user"` son pantallas que el usuario pide abrir: `semantic_intake` las elige leyendo el catálogo, el código valida y `chat._build_ui_actions` las emite como `{"type": "ui_action", "id", "label", "params"}`; agregar una es agregar un documento. **El agente solo ofrece las que el cliente declara en `ui_supported` (cuerpo del chat) y el plan permite** (`ui_offer`, lo calcula `_build_input`): un cliente que no declara nada no recibe ninguna. Campos opcionales del catálogo: `plans`, `confirm` (el frontend debe confirmar) y `label` por idioma. Contrato para el frontend: `doc/agente/UI_ACTIONS.md`. `source: "system"` (`connect_app`, `render_workflow`, `open_trigger`) las arma el código. Lo que `_build_ui_actions` lee debe estar en `ShifuOutputState`: `ainvoke()` no devuelve otros campos. Se mide con `scripts/eval_ui_actions.py` (~$0.01). `ui/flow.html` (`/ui/flow.html`, React + React Flow por CDN, sin compilar) es la prueba de un frontend que las ejecuta: botones por `ui_action` (tabla `HANDLERS`) y el workflow como grafo.
- **Archivos adjuntos (v0.11.0):** `POST/GET/DELETE /api/v1/files` (`app/routes/me/files.py`, `app/services/file_store.py`; ficha en Mongo `user_files`, tope 10 MB, extensiones y primeros bytes validados, todo por `user_id`). **Dónde van los bytes es intercambiable** (`app/services/file_storage.py`): `FILE_STORAGE=local` (por defecto, carpeta `SHIFU_UPLOAD_DIR` = `./uploads`, fuera de git) o `cloudinary` (crudo y privado, URL firmada; usa `CLOUDINARY_*`; **sin probar contra el servicio real**, no hay credenciales en el `.env`). Cada ficha guarda `storage` y `key`, así que al cambiar de servicio los archivos viejos se leen de donde están. Otro servicio = una clase con `put/get/delete` y una línea en `BACKENDS`. El chat recibe `files: [file_id]` y `_build_input` los convierte en `turn_resources` con URL `shifu-file://<id>`, que `document_analyzer` lee de Mongo; el chat nunca acepta una URL del cliente. `semantic_intake` recibe como hecho qué archivos vienen en el mensaje, los jueces reciben el documento como evidencia y `platform_knowledge.files` dice qué se puede adjuntar. Se mide con `python scripts/eval_files.py [base]` (~$0.05). Leer imágenes depende de `ocr_enabled` del plan.
- **Mini agente de código (solo con `SHIFU_DEV_UI=1`, fuera del grafo):** `POST /api/v1/dev/coder` (`app/routes/dev/coder.py`, 4o-mini) escribe un archivo de Python o de React. Python se ejecuta en un proceso aparte (10 s, carpeta temporal, sin variables de entorno) y, si falla, el modelo lo corrige con el error (hasta 2 veces). React lo ejecuta `/ui/coder.html` en un iframe aislado y manda el error de vuelta. La página guarda proyectos en `localStorage` (cada pedido es una versión sobre el código anterior: deshacer, pantalla completa, descargar un `.html` suelto). El iframe trae hechos `useLoop(fn, ms)` y `useKeys(fn)` y monta la app él mismo (`RUNTIME`): 4o-mini escribía mal el reloj y el teclado de los juegos. `CODER_MODEL` cambia el modelo (por defecto gpt-4o-mini). **Imágenes del usuario en la página:** el modelo escribe `<img src={IMAGES["nombre.png"]}>` y nunca los bytes; la página pide cada archivo a `/files/{id}` con el token (el iframe no lo tiene), arma `IMAGES` como data URLs y se lo pasa al iframe; el `.html` descargado las lleva dentro. El proyecto guarda `images: [{file_id, name}]`; las ya subidas viajan solo por nombre (`image_names`), no se vuelven a mandar al modelo. No es una caja de arena: no se expone a usuarios reales sin contenedor.
- **Principio: el código es mecanismo, el comportamiento son datos** (el usuario apuesta por el criterio del LLM y quiere poder pivotar de dominio). `agent_personality` trae, además de lo anterior: `voice` (cada clave se pinta tal cual en el prompt), `quality_control` (`enabled`, `max_retries`, `judge{model,mode}`, `checks[{name,criterion}]` del evaluador; con `mode: "per_check"` hay un juez mini por chequeo en paralelo y solo una falla "mayor" fuerza reescritura; el juez ve los últimos 6 mensajes), `platform_knowledge.rule` y `platform_knowledge.triggers` (como puede arrancar un workflow; sin ese hecho los jueces daban por inventado "cuando llegue un correo..."), en cada chequeo `blocking: false` (informa sin forzar reescritura; asi estan `answers_request` y `persona`, que no acertaron ni un "major" en la auditoria del 2026-10-10), `method: "claims"` (verificacion afirmacion por afirmacion: el juez clasifica y el codigo decide; "major" solo si una afirmacion queda contradicha por una linea que existe en el contexto y con polaridad opuesta) y `examples` (notas de calibracion sacadas de falsos positivos reales); si se agotan los intentos se entrega el borrador con menos fallas graves (`eval_drafts`), no el ultimo, `prompt_snippets` (`retry_correction`, `paused_commitment`), `mood_directives`/`effort_directives` y `greeting_behavior.applies_to_intents`. Si falta un campo, el código usa un respaldo genérico (3 chequeos, 2 reintentos). `prompt_mode: "brief"` cambia las directivas apiladas del responder (tono, esfuerzo, anti-loop, pausa, relevo del flujo de requisitos) por hechos de la situación (`helpers/situation.py`); sin el campo, todo sigue como antes. `SHIFU_AGENT_ID` elige qué documento se lee (p. ej. `shifu_v1` vs una variante mínima). Re-correr `seed_agent_identity.py` pisa los campos de primer nivel que un admin haya editado.
- `response_evaluator` corre en **todos** los turnos (centinela de calidad, con chequeos configurables) y `platform_context.py` arma el conocimiento real de la plataforma (catálogo y búsqueda sobre `app/functions`, indicando también lo que cada app NO puede hacer). El chat SSE acepta `trace` y `hold` en el body para la UI de pruebas en `ui/` (`/ui/`). **UI actions**: `_build_ui_actions` (chat.py) convierte los reportes de validacion en `connect_app` (uno por app que falte, con el nombre canonico del catalogo en `app` y `auth_type` oauth2/apikey/oauth1), se guardan con el mensaje (`save_message(ui_actions=)`) y `ui/app.js` los pinta como tarjetas (OAuth real con `/auth/<x>/login` traducido a `/integrations/<x>/login` con Bearer, formulario de API key en `/me/secrets`, y "Simular conexion" = `POST /api/v1/dev/connect/<app>`, solo con `SHIFU_DEV_UI=1`). Al conectar, la UI manda un turno `silent: true` (el agente lo recibe, no se guarda ni se pinta como mensaje del usuario). El flujo de requisitos (`req_nodes._app_reports`) corre los mismos validadores, para que tambien emita botones. Para que el popup OAuth termine en la UI: `FRONTEND_REDIRECT_URL=http://localhost:5001/ui/`.
- `main.py` monta automáticamente cada archivo de `app/integrations/providers/*.py` que exponga `router` en `/api/v1/integrations/<nombre>` (excepto `whatsapp`, que es webhook).
- Los límites por plan (modelos, `recursion_limit`, herramientas permitidas, cuotas) están en `app/billing/plans.py`. Los modelos permitidos y el esfuerzo (`low`, `medio`, `high`, `max`) se validan en `chat.py`.
- Variables que cambian modelos o límites: `V3_CHAT_MODEL`, `V3_MEMORY_MODEL`, `SHIFU_AGENT_ID`, `BIGTOOL_RATE_LIMIT_PER_HOUR`, `STEP_TIMEOUT_SECONDS`, `TOOL_MAX_RETRIES`, `CIRCUIT_BREAKER_THRESHOLD`.
